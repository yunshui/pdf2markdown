# 工作规则文档 (Workflow Rules)

## 文档概述

本文档定义PDF转Markdown工具项目的工作流程和决策规则，确保团队协作高效、决策透明。

**版本**: 1.0
**生效日期**: 2026-04-24
**适用范围**: 所有项目相关工作和决策

---

## 核心规则

### 规则1: 问题/需求处理流程

当遇到问题或接收到新需求时，必须遵循以下流程：

```
发现问题/需求
    ↓
分析原因
    ↓
提出解决方案
    ↓
等待确认
    ↓
获得同意后执行
    ↓
更新相关文档
```

#### 详细步骤

##### 1. 识别问题/需求
**输入来源**:
- 用户反馈的问题
- 测试发现的bug
- 新的功能需求
- 性能优化需求
- 代码质量问题

**输出**: 清晰的问题/需求描述

##### 2. 分析原因
**分析要点**:
- 问题/需求的根本原因是什么？
- 影响范围多大？
- 优先级如何（P0/P1/P2/P3）？
- 是否有临时解决方案？
- 是否有类似的先例？

**输出**: 原因分析报告

##### 3. 提出解决方案
**方案要素**:
- 具体的实施步骤
- 预估工作量和时间
- 潜在风险和应对措施
- 需要修改的文件
- 需要更新的文档
- 测试计划

**输出**: 完整的解决方案文档

##### 4. 等待确认
**确认方**:
- 功能相关: 产品负责人/用户
- 技术相关: 技术负责人/团队决策
- 文档相关: 项目负责人

**确认方式**:
- 明确的"同意"回复
- PR Review通过
- 会议决策记录

**注意**: 未获得明确同意前不得执行任何代码修改！

##### 5. 执行实施
**执行前提**:
- 已获得明确同意
- 方案已评审通过
- 测试计划已确认

**执行原则**:
- 按照方案逐步实施
- 及时汇报进度
- 遇到新问题立即停止并重新走流程

##### 6. 更新文档
**必须更新的文档**:
- README.md (如影响用户)
- technical.md (如影响技术实现)
- design.md (如影响设计)
- workflow.md (如影响流程)
- lessons-learned.md (如有新经验)

**更新检查清单**:
- [ ] 是否影响功能说明？→ 更新需求文档
- [ ] 是否影响API接口？→ 更新技术文档
- [ ] 是否影响数据结构？→ 更新设计文档
- [ ] 是否影响执行流程？→ 更新流程文档
- [ ] 是否有新经验教训？→ 更新经验教训文档

## 应用场景

### 场景1: 发现Bug

**示例**: API调用超时

**处理流程**:

1. **识别问题**
   - 问题描述: API调用频繁超时
   - 影响范围: 所有PDF转换
   - 优先级: P1

2. **分析原因**
   - 可能原因: 网络慢、文件大、超时设置不当
   - 根本原因: 超时时间设置过短
   - 影响评估: 中等

3. **提出解决方案**
   - 方案A: 增加默认超时时间到120秒
   - 方案B: 添加超时配置选项
   - 方案C: 实现更智能的超时策略
   - 推荐: 方案B (平衡灵活性和简单性)
   - 需修改: config.py, model_client.py
   - 需更新: technical.md, README.md
   - 预估: 30分钟

4. **等待确认**
   - 提交方案给团队评审
   - 等待明确同意

5. **执行实施** (获得同意后)
   - 修改代码
   - 编写测试
   - 运行测试

6. **更新文档**
   - 更新技术文档
   - 更新README配置说明

### 场景2: 新功能需求

**示例**: 添加进度条显示

**处理流程**:

1. **识别需求**
   - 需求描述: 长时间转换时显示进度条
   - 价值: 改善用户体验
   - 优先级: P2

2. **分析需求**
   - 技术可行性: 已安装tqdm，可直接使用
   - 工作量: 中等
   - 风险: 低

3. **提出解决方案**
   - 实施步骤:
     1. 在model_client中添加进度回调
     2. 在converter中集成进度显示
     3. 更新CLI支持进度条选项
   - 需修改: model_client.py, converter.py, main.py
   - 需更新: README.md, workflow.md
   - 预估: 2小时

4. **等待确认**
   - 提交方案给产品负责人
   - 等待明确同意

5. **执行实施** (获得同意后)
   - 按步骤实施
   - 测试进度显示

6. **更新文档**
   - 更新README使用说明
   - 更新流程文档

### 场景3: 文档更新

**示例**: API端点修复后更新文档

**处理流程**:

1. **识别需求**
   - 需求描述: 修复了API端点bug，需要更新文档
   - 影响文档: technical.md, workflow.md, lessons-learned.md

2. **分析影响**
   - 哪些部分需要更新
   - 是否会影响用户理解

3. **提出更新方案**
   - 具体更新内容
   - 更新章节位置

4. **等待确认**
   - 提交更新方案
   - 等待确认

5. **执行更新** (获得同意后)
   - 更新技术文档
   - 更新流程文档
   - 记录到经验教训

## 决策原则

### 优先级定义

| 优先级 | 定义 | 响应时间 | 示例 |
|--------|------|---------|------|
| P0 | 系统不可用，严重bug | 立即 | 服务崩溃、数据丢失 |
| P1 | 主要功能受影响 | 4小时内 | 转换失败、API错误 |
| P2 | 次要功能受影响 | 24小时内 | 进度显示、小bug |
| P3 | 优化需求 | 计划内 | 性能优化、文档完善 |

### 决策者

| 决策类型 | 决策者 | 说明 |
|---------|--------|------|
| 功能优先级 | 产品负责人 | 确定需求优先级 |
| 技术方案 | 技术负责人 | 审批技术实现方案 |
| 文档变更 | 项目负责人 | 确保文档一致性 |
| 发布决策 | 团队共识 | 是否发布新版本 |

### 决策标准

**同意实施方案的条件**:
- ✅ 方案完整且可行
- ✅ 风险可控
- ✅ 工作量合理
- ✅ 有明确的测试计划
- ✅ 包含文档更新计划
- ✅ 优先级符合当前资源

**拒绝实施的情况**:
- ❌ 方案不完整
- ❌ 风险过高
- ❌ 工作量超出预期
- ❌ 缺少测试计划
- ❌ 未考虑文档更新
- ❌ 与现有架构冲突

## 沟通规范

### 方案提交格式

```markdown
# 问题/需求: [标题]

## 问题描述
[详细描述问题或需求]

## 原因分析
[分析根本原因]

## 解决方案
[详细的解决方案]

### 实施步骤
1. [步骤1]
2. [步骤2]
3. [步骤3]

### 影响评估
- 需修改的文件: [文件列表]
- 需更新的文档: [文档列表]
- 预估工作量: [时间]
- 潜在风险: [风险列表]

### 测试计划
[如何验证方案有效]

## 请求确认
请确认是否同意执行此方案
```

### 确认回复格式

**同意**:
```
✅ 同意执行
- 理由: [可选说明]
- 建议: [可选建议]
```

**拒绝**:
```
❌ 拒绝执行
- 理由: [详细原因]
- 建议: [改进建议或替代方案]
```

**需要修改**:
```
⚠️ 需要修改
- 修改意见: [具体需要修改的地方]
- 请完善后重新提交
```

## 异常处理

### 流程中断

如果执行过程中发现新问题:

1. **立即停止执行**
2. **记录当前状态**
3. **分析新问题**
4. **提交新的方案**
5. **等待确认后继续**

### 紧急情况

对于P0级别的紧急问题:

1. **立即通知相关人员**
2. **简要分析原因**
3. **提出临时方案**
4. **快速决策执行**
5. **事后补充完整流程**

## 违规处理

### 违规行为

以下行为视为违规：

1. **未获同意擅自修改代码**
2. **修改代码后不更新文档**
3. **跳过分析直接实施**
4. **提交不完整的方案**
5. **不按流程处理紧急问题**

### 处理措施

| 违规类型 | 首次违规 | 再次违规 | 严重违规 |
|---------|---------|---------|---------|
| 擅自修改代码 | 警告 | 回滚代码 | 暂停权限 |
| 不更新文档 | 警告+补充更新 | 记录过失 | 暂停权限 |
| 跳过流程 | 警告 | 重新走流程 | 暂停权限 |
