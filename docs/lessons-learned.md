### 1.2 API端点URL处理

#### 经验
**问题**: API端点URL格式不统一导致重复添加`/v1/`

**错误示例**:
```python
# 原始代码（有bug）
if endpoint.endswith('/'):
    endpoint = endpoint + 'v1/chat/completions'
else:
    endpoint = endpoint + '/v1/chat/completions'
# 问题: https://api.com/v1/ → https://api.com/v1/v1/chat/completions
```

**正确做法**:
```python
# 修复后
endpoint = endpoint.rstrip('/')
endpoint = endpoint + '/chat/completions'
if '/v1/' not in endpoint:
    endpoint = endpoint.replace('/chat/completions', '/v1/chat/completions')
```

**教训**:
1. URL路径处理需要考虑各种格式变体
2. 先标准化（如rstrip）再处理
3. 使用条件判断避免重复

#### 建议
- 编写单元测试覆盖各种URL格式
- 考虑使用URL解析库（如urllib）
- 在文档中明确支持的URL格式

### 1.3 重试机制实现

#### 经验
**问题**: 重试逻辑中的max_retries计算错误导致无限重试

**错误示例**:
```python
# 错误的实现
max_retries = retry_count + self.max_retries if retry_count > 0 else self.max_retries
# 问题: 每次递归调用，max_retries都在增加
```

**正确做法**:
```python
# 正确的实现
max_retries = self.max_retries
# 固定使用配置的max_retries值
```

**教训**:
1. 递归重试时，重试上限应该是固定值
2. 使用测试用例验证边界条件
3. 添加超时保护防止无限循环

#### 建议
- 为重试机制编写压力测试
- 考虑使用装饰器模式实现重试
- 添加最大重试时间限制（除次数外）

### 1.4 配置管理设计

#### 经验
**问题**: 需要支持配置文件和命令行参数覆盖

**解决方案**: 深度合并配置
```python
def _deep_merge(base, override):
    result = base.copy()
    for key, value in override.items():
        if key in result and isinstance(result[key], dict):
            result[key] = _deep_merge(result[key], value)
        else:
            result[key] = value
    return result
```

**教训**:
1. 配置覆盖需要深度合并，不是简单替换
2. 默认配置应该保证最小可用性
3. 配置验证很重要

#### 建议
- 使用专门的配置管理库（如pydantic）
- 添加配置格式验证
- 提供配置模板和示例

#### 经验
**问题**: 图片转换和传输影响性能

2. 选择合适的DPI（200 DPI平衡质量和大​​小）
3. PNG格式在质量和大小间取得平衡

**性能数据**:
- 磁盘I/O: ~50ms/图
- 内存I/O: ~5ms/图
- 改进: 10倍提升

#### 建议

- 添加图片质量参数可配置

## 4. 错误处理经验

### 4.1 异常分类

#### 经验
**问题**: 所有错误统一处理不够灵活

**改进**: 根据错误类型采用不同策略

| 错误类型 | 处理策略 | 是否重试 |
|---------|---------|---------|
| FileNotFoundError | 立即失败 | ❌ |
| ValueError (配置) | 使用默认值 | ❌ |
| Timeout | 重试N次 | ✅ |
| ConnectionError | 重试N次 | ✅ |
| HTTP 4xx | 不重试 | ❌ |
| HTTP 5xx | 重试N次 | ✅ |

#### 建议
- 定义清晰的错误处理策略
- 为不同错误类型设置不同的重试次数
- 添加错误恢复机制

## 10. 用户体验经验

### 10.1 超时时间设置

#### 经验
**问题**: 默认超时时间60秒对于复杂页面太短，导致转换失败

**实际案例**:

- API响应超过60秒，重试3次后失败

**分析**:
- 不同PDF页面复杂度差异很大
- 简单页面: ~30秒响应
- 复杂页面: ~90秒响应
- 统一超时时间不够灵活

**改进**:
- 将默认超时从60秒增加到120秒
- 允许用户自定义超时时间
- 考虑动态调整超时（未来）

#### 建议
- 设置合理的默认值（根据实际测试）
- 提供配置选项覆盖默认值
- 在文档中说明超时时间的影响
- 考虑基于页面复杂度的智能超时

### 10.2 容错机制

#### 经验
**问题**: 单页失败导致整个转换失败，用户必须重新开始

**实际案例**:
- 87页PDF转换到第4页时超时失败
- 前3页已成功处理但丢失
- 用户必须重新转换整个文档
- 大型PDF转换成本高，失败代价大

**教训**:
1. **单点故障不可接受** - 不能因为一页失败而全部失败
2. **进度必须持久化** - 已完成的工作不能丢失
3. **失败信息必须明确** - 用户需要知道哪些页面失败及原因
4. **恢复机制必要** - 支持从断点继续

**改进方案**:
1. 单页失败时跳过继续处理
2. 生成失败页面占位符文件
3. 记录失败原因到日志和状态文件
4. 转换完成后生成失败报告

#### 建议
- 设计失败页面占位符格式统一
- 失败报告应包含所有失败页面和原因
- 考虑自动重试失败页面
- 提供单独转换失败页面的工具

### 10.5 时间预估算法

#### 经验
**问题**: 用户不知道还要等多久，无法合理安排时间

**实现方案**:
```python
def get_estimated_remaining_time(self):
    avg_time = get_average_time()
    remaining_pages = total_pages - completed_pages
    return remaining_pages * avg_time
```

**改进**:
- 使用滑动平均，减少早期页面的影响
- 考虑网络波动的影响
- 显示预估时间范围而非固定值
- 根据页面类型调整权重

#### 建议
- 时间预估应有合理的误差范围
- 随着处理进度更新，预估会更准确
- 首次转换预估可能不准确
- 记录历史数据改进预估精度

### 10.6 控制台输出优化

#### 经验
**问题**: 日志输出到控制台干扰进度显示

**问题分析**:
- INFO级别日志包含大量详细信息
- 进度条输出被日志信息覆盖
- 用户无法看到清晰的进度

**改进方案**:
1. 分离日志级别：文件用DEBUG，控制台用WARNING+
2. 进度信息单独显示，不在日志中重复
3. 使用tqdm的动态刷新
4. 限制控制台输出的详细程度

**代码实现**:
```python
# 控制台输出进度（不在日志中）
print(f"\r[Processing] Progress: {percent}%", end='', flush=True)

# 日志记录详细信息
logger.info("Page conversion details", ...)
```

#### 建议
- 控制台输出要简洁
- 关键信息同时输出到日志和控制台
- 考虑提供-v/--verbose选项显示详细日志
- 支持静默模式（-q/--quiet）

### 10.7 失败报告生成

#### 经验
**问题**: 转换失败后用户不知道哪些页面失败及原因

**改进方案**:
1. 在主索引文件中添加失败页面章节
2. 列出所有失败页面和错误信息
3. 提供解决建议
4. 生成独立的失败报告文件

**失败报告内容**:
```
## 转换失败的页面

- **页面 4**: Request timeout after 3 retries
- **页面 17**: Connection error
- **页面 42**: HTTP 500 error

## 建议解决方案

1. 增加超时时间: --timeout 180
2. 检查网络连接
3. 验证API密钥
4. 使用 --resume 从失败处继续
```

#### 建议
- 失败报告要清晰易懂
- 提供可操作的解决建议
- 区分不同类型的错误
- 考虑生成JSON格式的报告（便于程序处理）
